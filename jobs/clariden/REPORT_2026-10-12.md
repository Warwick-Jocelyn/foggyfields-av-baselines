# SplatAD on NFF — reproduction report (Clariden GH200, 2026-10-12)

**Question.** Do the SplatAD results published with `foggyfields-av-baselines` /
`JocelynW/foggyfields-av-baseline-checkpoints` reproduce on the NFF release of the same clips?

**Answer.** Yes, exactly — and the reproduction shows that those numbers describe a model that does not
actually reconstruct the scene. Both published checkpoints, evaluated on the NFF copy of their clips, return
their published PSNR to two decimals (24.60 / 23.94), proving the NFF data, split and metric pipeline are
identical to the original setup. Retraining from scratch on GH200 with the published config lands within
0.5–0.8 dB (25.05 / 24.74). But every one of these models — the published checkpoints included — renders
gray, structure-less views on both held-out **and training** frames. In fog, a near-constant image already
scores ~24–25 dB, so PSNR hides the failure. LiDAR geometry, by contrast, is reconstructed reasonably
(Chamfer 0.63–1.40 m), because LiDAR supervision is dense and direct.

Clip-ID map: the checkpoint repo uses the old AVFog ids. `clip003_residential-light-fog` = **NFF-02**,
`clip004_highway-heavy-fog` = **NFF-03**.

Runs: `published ckpt` = the Hugging Face checkpoint evaluated on the NFF copy; `faithful` = retrained with
the published code and config (no mask, LiDAR read as before); `corrected` = retrained with the valid-pixel
mask in the RGB loss and LiDAR sweeps read in their true sensor frame (§3). Protocol everywhere: nvs_50_50
(odd frames held out), 30k iterations, seed 42, MCMC cap 5 M, 2 M seed points, camera-opt off.

## 2. LiDAR geometry — SplatAD's native LiDAR rasterisation, 99 held-out sweeps per clip

CD = symmetric mean nearest-neighbour distance between the rendered point cloud (ray-drop applied, as in the
model's own eval) and the GT sweep, metres, lower is better — the June-2026 definition. CD² = nerfstudio's
`chamfer_distance` (sum of squared NN distances both ways / |GT|, m²). RCD = CD / mean GT range. Depth
median L2 = median |pred − GT| range over returned rays.

| Clip | Run | CD (m) | CD² (m²) | RCD | depth median L2 (m) |
|---|---|---|---|---|---|
| NFF-03 | published ckpt on NFF | 1.402 | 31.90 | 0.0507 | 2.82 |
| NFF-03 | faithful | **1.005** | **14.77** | **0.0363** | **2.13** |
| NFF-03 | corrected | 1.181 | 30.89 | 0.0433 | 2.64 |
| NFF-02 | published ckpt on NFF | **0.633** | **4.16** | **0.0257** | **1.02** |
| NFF-02 | faithful | 0.731 | 4.59 | 0.0297 | 1.28 |
| NFF-02 | corrected | 0.647 | 4.65 | 0.0267 | 1.28 |

Reference, June-2026 Clariden study on NFF-02 (original config): SplatAD CD 1.199 m / RCD 0.0487, NeuRAD
0.355 / 0.0144. The June script was lost in the scratch purge, so its exact point-cloud filtering may differ
from this one; the ordering SplatAD ≫ NeuRAD is unchanged. Ray-drop accuracy is 1.000 for every run and is
omitted: NFF rasters contain only returned rays, so the ray-drop classifier is never tested.

Reading: LiDAR geometry is fine (sub-metre to ~1.4 m on 20–30 m scenes) while RGB is a blur — the Gaussians
sit on the right surfaces but the appearance never converges. CD is self-consistent per run (each model is
scored against the LiDAR in the frame it was trained with), so it does not expose the 1.94 m LiDAR/camera
offset of the faithful runs; the corrected variant removes that offset and improves RGB, but does not
improve CD (NFF-03 slightly worse).

The old camera-depth metric (`compute_lidar_metrics.py`, published 8.63 / 15.20 m) also reproduces exactly
from the published checkpoints when its math is replayed, but it is meaningless for SplatAD: the camera depth
is gsplat's alpha-weighted expected depth, which saturates at ~10–17 m in fog. Those numbers are kept in
`RESULTS.md` for traceability only.

## 3. What the validator found in the code (fixed on branch `clariden-nff-repro`)

| Finding | Evidence | Status |
|---|---|---|
| LiDAR sweeps are in the **sensor** frame, not ego | raw ground plane at z = −2.00 m (cameras at 0.8–1.4 m); 0 vs ~1000 points/frame inside the 3-D boxes before/after `T_lidar_rig` | dataparser flag `lidar_points_frame=sensor` (default keeps the old behaviour) |
| Valid-pixel masks never used | `mask_filenames=None`; 18–25 % black pixels in loss and PSNR | dataparser flag `use_valid_masks` |
| `compute_lidar_metrics.py` wrong projection | 3-D→2-D boxes reproject with 0.000 px error only with `inv(T_camera_rig)` | replaced by `jobs/clariden/lidar_metrics.py` (legacy math kept for traceability) and `lidar_chamfer_eval.py` |
| `splits_json=auto` | per-sensor linspace 0.5 == `nvs_50_50` exactly | confirmed, no change |
| CONVENTIONS.md / nff-toolkit | say "ego frame" / apply `inv(T_lidar_rig)`; both wrong for this release; per-point timestamps are ±50 ms offsets, not absolute | documented; toolkit fix suggested |

The July-2026 memory note claiming ego-frame sweeps was based on a points-in-box match that was a match of
zeros; it has been corrected. The LiDAR-NFF-Benchmark adapters ("ego pts as-is") inherit the same offset
for all four methods — rankings are probably unaffected but it should be re-run before publication.

## 4. Why SplatAD's RGB fails here (hypotheses, not yet tested)
The corrected variant removes the 1.94 m LiDAR/RGB conflict and the mask noise and gains 2 dB, but renders
are still blur. Remaining suspects from the June root-cause analysis: all 7 cameras are stamped with the
LiDAR spin-centre time (true per-camera trigger offsets are ±50 ms → ~1 m at 20 m/s), `rolling_shutter_time
= time_to_center_pixel = 0`, and MCMC relocation churn at the 5 M cap. NeuRAD/EmerNeRF reconstruct these
clips fine, so the data is sound.
